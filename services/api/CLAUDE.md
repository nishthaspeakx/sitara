# services/api — FastAPI modular monolith (SPEC §6.3)

Bounded-context modules in one process (auth, users/profiles, localisation, astrology facade, daily-guidance, chat-orchestration, memory, notifications, payments, safety, admin-api, …), typed in-process interfaces, extraction path pre-planned.

## Rules
- Errors: ONLY the §34.4 envelope from `sitara_schemas` — never a custom shape. HTTP status per the §6.3 convention.
- LLM never computes astrology — facts come from the astrology facade over sitara-astro (§5.3).
- All strings via i18n keys; idempotency keys on all mutation endpoints; no secrets/PII in logs (§13).

## panchang module (M3, §5.2 Layer B/D) — invariants that must not regress
- **No majority vote anywhere.** §32.2 replaced §5.2 Layer D's "majority source" with an authority rule. `adjudicate.py` is pure and vote-free; a test parses its AST to keep it that way.
- **Layer A is never outvoted** on deterministic astronomy (boundary instants, sunrise/sunset) — vendor disagreement raises a review flag, never `disputed`. When Layer A cannot answer, §32.2's DivineAPI-primary rule takes over (`FactClass.PANCHANG_ASTRONOMY`).
- **Prokerala is never persisted** — ToS. `PanchangCache.put` raises on it; Layer-A fallbacks are recomputed, not stored. So exactly one provider occupies a panchang row and §6.4's uniq index holds.
- **Cache keys are global** (`sitara_schemas.cache_keys`, §7.2) — a user id in one would fan a person's data across everyone sharing the row.
- **Provider shapes: Prokerala VERIFIED (live sandbox, 2026-01-01), DivineAPI still unverified** — its real endpoint paths are unknown (every guess 404s) and are env-overridable via `DIVINEAPI_PATH_*`. See `tests/panchang/fixtures/README.md`; the skipping provenance test is the honest marker — do not delete it.
- **Prokerala quirks are load-bearing:** krishna-first tithi ids (rotate 15), 0-based nakshatra ids, `index` always 0, offset-bearing `datetime` required, and NO typed muhurat finder (a typed query is declined, never faked).
- CI never calls a vendor: `test_no_live_network.py` blocks DNS + connect for non-loopback.

## db module (M4, §6.4) — invariants that must not regress
- **`db/registry.py` is the only declaration of database shape.** `ensure_schema`, `verify`, `csfle` and the migration runner all read it. Never create a collection or index anywhere else.
- **`tests/db/test_registry_matches_spec.py` parses §6.4 out of `docs/spec/SPEC.md`** and fails on any divergence — retention, shard key, encryption marks, index list. Edit the spec or the registry and the other must follow. Do not weaken this test.
- **Every index beyond §6.4's cell carries a `cite`;** every collection outside the table cites the section that mandates it (§22.5, §25.7, §14-deploy). Undeclared = drift = `verify` exits 1.
- **TTL indexes exist only where §6.4 says "TTL"** (panchang_cache 90d, transit_cache 400d, notifications 180d, story_views 90d per §25.7). Prose retention ("8 years (tax)", "7 years, append-only") is a job's problem — a TTL index there deletes records the spec says to keep, and `verify` fails on it. See §36.2.
- **`transit_cache` uniq is `(date, band, engine_semver)`** — §6.4's `(date, band)` extended per §7.2's key grammar; recorded as §36.1, and a test keeps the extension sourced.
- **CSFLE is explicit, never automatic** (automatic is Atlas/Enterprise-only; dev is Community). Local KMS refuses outside dev/test; deterministic only for the §33.2 contact replicas. `memories.embedding` stays in the clear — you cannot vector-search ciphertext.
- **`voice_sessions` and `call_sessions` structurally reject any audio field** (§13/§33.1). The validator does it, not a convention.
- **Seeds are synthetic only** (§22.12): `@example.invalid` emails, +9199999 phones, `synthetic: true` on every doc; the seeder refuses a non-dev environment or a non-local host.
- Every document carries `created_at`/`updated_at`/`schema_v` — use `db.documents.stamp()`, the validators enforce it.

## chat_orchestration module (M5, §9) — invariants that must not regress
- **The stage order in `pipeline.py` IS §9's mandatory pipeline.** `Stage` names every step; `test_stage_order_is_the_spec_order` reads the trace and asserts the sequence. Adding a stage means editing the spec first.
- **Cite-or-die is mechanical, not prompted.** `grounding.py` rejects (a) an uncited astrological claim, (b) a `[[fact:…]]` id absent from the served payload, (c) a number not in the cited snapshot, and (d) **a sentence about a different BODY from the fact it cites** (M8-P10). (d) is the one (a)–(c) cannot see and the one that has actually shipped: "Venus is in your 10th house" citing Saturn's 10th-house fact passes every numeric test, because the 10 is in the fact verbatim. CL-009 is that shape with the Moon and the Sun. It compares **like with like** — grahas against grahas, nakshatras against nakshatras — because a panchang nakshatra fact holds no graha at all and comparing across classes failed `moon_nakshatra_note` for being right. Locale surfaces come from `terms.*` in the i18n catalogs (§14-reviewed); `policy/claim_terms.json`'s `celestial` block, now keyed by canonical body, carries only the synonyms the catalog lacks (बृहस्पति beside गुरु). **That block feeds two other readers as a flat set** — restructuring it once handed them the dict's keys and every Devanagari graha name silently left the claim net. The claim lexicon is derived from the `sitara_schemas` enums plus `policy/claim_terms.json`; **strong vs weak matters** — a weak term needs a number beside it, or Tara could never say "I don't have your birth chart yet" without failing her own validator.
- **Exactly ONE corrective regeneration**, then the safe fallback line + `safety_events` review row (§9, §2.4 rule 8). `ChatSettings` raises if anyone sets it to anything but 1.
- **L4 never reaches the model** (§22.9) — templated, instant, machine-delivered, queued for human oversight. L2+ removes astrology *at routing*, so no fact tool is even called.
- **The §22.8 allowlist is applied in code** after the router speaks (`TOOL_ALLOWLIST`), never by asking the model nicely.
- **A tool that cannot answer declines** (`FactToolUnavailable`) and the turn goes to a template. Granted tools returning nothing → `chat.data.cannot_calculate`; handing the model an empty payload plus a chart question is the shape of a fabrication.
- **The trace records shapes, not content** (§13): `TurnTrace` hashes text unless `trace_capture_content`, which `build_tracer` refuses outside dev/test. Langfuse-shaped events go through a `TraceSink`.
- **System blocks are the cached prefix** (§9): persona → citation contract → locale style guide, most-stable first. Nothing per-turn above the breakpoint, or every user's cache dies every turn. Bump `prompts.PROMPT_VERSION` on any edit.
- **A blank `ANTHROPIC_API_KEY` is "provider down", not a boot failure** — `build_pipeline` returns None and `/v1/chat/turn` serves the §34.4 `SYS_UNAVAILABLE` envelope.
- **Identifiers become ObjectIds at the store boundary, nowhere else.** §6.4 types `messages.conversation_id`, `guidance_logs.user_id` and `guidance_logs.message_id` as `objectId`; the pipeline carries §33.2's product identity as a string. `store.to_object_id` is the single conversion and refuses a non-`_id` loudly. **`tests/chat/test_store_mongo.py` writes through the real §6.4 validators** — it exists because the in-memory fake once accepted strings the real collection rejected, so the whole suite was green while every real write failed. Do not delete it, and keep `InMemoryMessageStore` minting real ObjectIds.
- **An outage is not a safety event.** A provider failure serves the fallback line and does NOT queue a human (§8 degradation); only a validator double-failure or an L4 writes `safety_events` (§22.9's 24h SLA). `safety_events.classifier_scores` carries the real L1 labels plus the trigger, CSFLE-encrypted under the `safety` key class.
- **The cache breakpoint goes after the last STABLE system block**, never simply on the last one — `LLMRequest.cacheable_prefix_len` carries it. Below the breakpoint sits the per-turn safety register; inside it, every L2+ turn would be a cache write instead of a read.
- **The service renders §9's safety and decline strings itself**, so `packages/i18n/messages` ships in the image and `localisation.verify_catalogs` refuses to boot without them. Discovering a missing catalog when an L4 turn needs the crisis line is the one failure mode worth a startup crash.
- **A term with a space has more than one spelling** (CL-015). Every multi-word strong term was listed in exactly ONE, so closing a single space walked a claim past the validator in all three locales — "Rahukaal today runs from 3:00 PM to 4:30 PM" passed UNCITED, with real clock values in it, and `sun sign`/`moon sign`/`rising sign`/`चंद्र राशि` were all the same. Surfaced by the M9 live run (Ink transcribes spoken "rahu kaal" as "Rahukaal") but never about STT: grounding validates what TARA says, and a transcript never reaches it. `_separator_variants` now DERIVES the joined and hyphenated forms inside `_alternation`, so a term added to the JSON tomorrow is covered without anyone remembering. The celestial surface MAP is deliberately not expanded — its pattern and its lookup table must stay in step, and no celestial surface is multi-word.
- **The claim lexicon's word boundaries are load-bearing** in both validators: "Tara" inside "tarah" (everyday Hinglish) once failed ordinary replies and burned the single regeneration.
- **Open §31.3 item — CLOSED as §37 (CC-004):** §9's sampling control is capability-relative. The pipeline declares 0.2/0.7; `llm.py` applies them where the pinned model accepts them and records `temperature_declared` + a trace note where it cannot. Do not quietly delete the declaration.
- **Release gates:** `uv run python -m sitara_api.release_gates` reports the human-closed §31.7 gates (helpline table, both safety corpora). `/shipcheck` runs it; three are open and block closed beta.

## voice module (M9, §33.1/§25.4/§3.2) — invariants that must not regress
- **`voice/service.py`'s step order IS the design**, and each step is where it is for a reason that has cost someone something: store the ORIGINAL before STT (§28.3 — "transcribe-fail → 'send as text?' original audio preserved"; storing after a successful transcript loses exactly the recordings a user most wants back), then transcribe, then run `pipeline.run` — **the same method `POST /v1/chat/turn` calls, not a variant** — then synthesise from `TurnResult.text`.
- **Voice is not a §9 bypass, and it has TWO directions.** Inbound is obvious: a spoken question meets every validator a typed one does, stage for stage. Outbound is the subtle one — if synthesis read the model's draft rather than the presented turn, the audio would carry the sentence grounding REJECTED while §25.4's transcript toggle showed the one it accepted. No validator can see that; by the time grounding runs the draft is already at the synthesiser. `tests/voice/test_grounding_parity.py` holds both lines from outside.
- **§33.1's ephemeral mode is an ABSENCE, not a cleanup.** With "delete my audio after transcription" on, the asset is never written — a row that exists for a moment is a row in a backup, a replica and an oplog. The preference also fails CLOSED toward privacy when unreadable.
- **`voice_assets` retention is a JOB, never a TTL** (`voice/expiry.py`). A TTL reaper deletes the document, so it would destroy the `deleted_at` tombstone §33.1 requires in the same sentence — and a bubble cannot say "this recording has expired" if the row is gone, because a missing row and a never-existed row are the same absence. Per-note delete is deliberately the SAME code path.
- **`assert_storable` is shared by the real store and the in-memory fake.** §25.4's promise breaks as a wiring mistake — a user bubble whose source-audio id points at the synthesised asset — which would look right in every test that checks "audio plays". A fake that accepted it would be a defect in the fake (the root rule, and the one M5 broke).
- **The locale→language map is declared data, not a prefix rule.** `hi-Latn` → `en` for STT (Latin script) and → `hi` for TTS. Verified live: Ink returns Devanagari for the Indic span under `language=hi`. Getting this wrong is invisible to every accuracy metric — the words are right and only the script is wrong (CC-009 §42.2).
- **A sequence gap FAILS the note** (`voice/audio.py`, and again in the socket). A note missing its middle still transcribes, into a fluent sentence the user never said, which reaches §9 as their question. §9 gates what TARA says; this fabrication is on the user's side of the turn.
- **Cartesia is VERIFIED in BOTH modalities now** — batch on 13 Aug 2026, streaming on 15 Aug 2026 (`tests/voice/fixtures/streaming_en.json`). The streaming half shipped UNVERIFIED and the first live call corrected it: **`context_id` is required on the TTS websocket**, and without it Sonic errors on every utterance, so a call reached her validated words and fell silent every time. 1,457 tests were green — none reaches a vendor. Sarvam remains UNVERIFIED in both.
- **`tts_stream_body` is the ONE Sonic request body**, shared by the adapter and `record_streaming.py`. The recorder used to rebuild it while claiming to use the adapter's, and that divergence cost a live cycle: the adapter was fixed, the recorder still sent the old shape, and the identical vendor error read as "the fix did not work". A fixture recorded from a request the adapter does not send proves nothing about the adapter.
- **Ink emits a final PER PHRASE, not per utterance** (recorded, 15 Aug 2026). One spoken sentence came back as two `is_final` frames, so a speaker who pauses mid-thought currently has their sentence cut in two and answered twice. Known and NOT yet handled — the debounce length is a product decision.
- **`RedisMetricStore.counters()` scans the namespace; it must never GET by enum name.** Doing so raised `WRONGTYPE` on the latency reservoir the moment a real call recorded a sample, and never saw the per-locale safety keys at all — so §33.5's one per-language measure could not have produced a number. `InMemoryMetricStore` keeps counters and samples in separate dicts and cannot make either mistake, which is precisely why the tests missed both.
- **§3.2's acceptance gate is FINAL and NOT MET.** The adapter existing is not the gate passing. Ink's streaming endpoint is English-only today (batch carries 49 languages, which is what voice notes use) and Ink documents no code-mix mode — the Hinglish claim is Sonic's, on the TTS side.

## call gate + routing (P10b, §25.3/§33.5/CC-010) — invariants that must not regress
- **`routing.resolve()` may return NO provider, and that is a designed state.** There is no fallback parameter, no `or CARTESIA` and no default argument anywhere in that module — a sensible-looking default is exactly how CC-010's ruling gets reversed by accident. A test asserts the signature stays that way.
- **Batch and streaming availability differ for the same vendor, model and language.** Voice notes (batch) work in all three locales; calls (streaming) work only in `en`. `calls_available_in` and `voice_notes_available_in` are separate functions on purpose — one "voice works" boolean would take voice notes down in hi/hi-Latn for a limitation that has nothing to do with them.
- **Landing Sarvam is ONE cell** (`DECLARED` → `IMPLEMENTED`) plus an adapter. `test_landing_sarvam_streaming_is_ONE_cell` asserts that literally, and restores the matrix in a `finally` — a leaked mutation would make every other routing test pass for the wrong reason.
- **`call_gate` distinguishes BLOCKED from FAILING, and neither is PASSING.** §33.5's safety-interception and naturalness measures cannot run in hi/hi-Latn at all, so they are BLOCKED; an unmeasured measure is UNMEASURED. `passes` requires all six PASSING, because §33.5 says "only if". The blocked reason is READ from the routing matrix so the harness unblocks on the commit that unblocks it.
- **The `call.indic_streaming_stt` gate reads the matrix too**, for the same reason: an amber-forever gate is how a real blocker gets tuned out.
- **`speak_holding_phrase` takes NO text, and the signature is the guarantee.** §25.3's phrase needs arbitrary words synthesised, which is exactly the shape that would undo `speak()`'s parity rule: one `speak_text(text: str)` on `CallTurnService` and a future caller can hand the synthesiser a model draft, with the audio carrying the sentence grounding REJECTED while the caption shows the one it accepted. The words come from the catalogs by INDEX; a draft is unrepresentable in the signature, and a test asserts the parameter set rather than only today's behaviour.
- **The phrase is not a turn.** Nothing stores it, §9 never runs for it, and it makes no claim — so there is nothing for cite-or-die to validate and nothing to leak into §30.5's Journal, §32.11's handoff transcript or tomorrow's memory retrieval.
- **The phrase is AWAITED before her answer's audio.** Both write PCM to one socket, so overlapping them interleaves two voices into noise. It runs through `self._speech` so §25.3's barge-in reaches it — filler is the thing it should be easiest to interrupt — and a barge-in over it does NOT abandon the answer §9 has nearly finished paying for.
- **Its keys are in `SERVER_RENDERED_KEYS`**, so a missing Hindi phrase fails at BOOT rather than 1.8 seconds into a live call in exactly the locale the phrase exists to hold. §2.4 has no English fallback, so a lookup failure becomes silence, never the wrong language.
- **§3.4 respellings reach the SYNTHESISER and nothing else.** One call site, on the way into `SynthesisRequest`, after the turn is stored and after it has crossed the wire. A leak would put "raahoo kaal" in the user's own thread and make §25.4's transcript toggle disagree with itself. Every row is `draft`; production serves only reviewed rows.

## calls module (M9-P10b, §25.3/§25.7) — invariants that must not regress
- **`calls/service.py`'s order is `voice/service.py`'s rule applied to a different irreplaceable thing.** A note stores the AUDIO first (§28.3); a call commits the TRANSCRIPT first, because call audio is never stored at all and the transcript is the only record there will ever be. §9's `_persist` writes both messages at the END of a turn, so an LLM outage between "she heard you" and "she answered" used to erase what somebody said out loud — permanently, with no audio to fall back on and no composer to resend from. `commit_utterance` is what stops it and `TurnRequest.user_message_id` is what keeps the pipeline from then writing the turn twice.
- **A call's user message is `transcript_only`, never `text_only`.** `text_only` means "a typed message; there is no audio and no control", which would render a call in the thread as though the user had used the keyboard. No validator catches that and the transcript screen renders it without complaint.
- **The GRANT is where every refusal happens** (`POST /v1/call/session`): §33.5's flag, CC-010's locale ruling, §7.3's exhausted pool. A refusal on an open socket has to be drawn as a call that failed; a refusal on the grant is drawn as an affordance that was never offered.
- **`calls_enabled` defaults to FALSE and that is §33.5, not caution.** Calls ship "ONLY if" six measures pass; two are BLOCKED by CC-010 and two are UNMEASURED. Turning it on is a decision made against `voice.call_gate`'s table.
- **`call_metrics` collects §33.5's evidence and `call_gate` scores it, and they are separate files on purpose.** A gate that collected its own evidence could be made to pass by changing how it counts. Four measures are real; `cost_per_call_user` and `call_naturalness` are deliberately ABSENT from `observed()` — a rate card and a human panel are not things instrumentation produces, and a plausible constant would make the cheapest measure to fake the one the gate reads.
- **The safety measure reads the WORST locale, never the average** (§33.5's "in all 3 languages", §18's "no averaging across languages, ever"). An average lets a perfect English score carry a language that intercepts nothing.
- **`MinuteLedger` fails toward the SMALLEST pool.** An unreadable subscription is `CallPlan.NONE`, and an unrecognised plan string is too — §30.3 already contemplates plans this code has never seen, and the failure worth having is "calls unavailable" rather than a silent grant of somebody else's quota. The mirror image of §33.1's fail-closed-toward-privacy.
- **§7.3's unlimited tier has NO invented ceiling.** §7.3 names no number for its soft limit, so `quota_minutes` is None, no warning fires and no call is cut on it.
- **`chat_orchestration/birth.py` exists so the call reaches the SAME §5.3 narrowing.** The bug it was extracted from — every turn running with an all-False `BirthProfile()` — was invisible to every test because every test passed a profile in explicitly, and was found by the first live conversation. A second narrowing would be found the same way.

## journal / family / reflection (M10, §30.5/§32.15/§45) — invariants that must not regress
- **The Journal is a VIEW, not a collection.** `journal.service.timeline` merges `daily_briefings`, `night_reflections`, `call_sessions.summary` and CC-011's `journal_saves`, plus derived milestones. Nothing is copied, and a saved turn is rendered by going and READING the message — a test edits the source and re-reads to prove it.
- **A save is a POINTER (CC-011 §44.2).** `journal_saves` has no field a sentence could occupy, and `SaveRequest` has none either. A copy would outlive its artefact and make §30.5's "delete a journal entry → artefact removed" false for exactly the guidance someone cared enough to keep.
- **`MemoryService.forget()` writes a content-free withdrawal to `consents`** (CC-011 §44.5) — the §32.4 type, when consent was granted, when withdrawn, the surface. Not the content and **not the memory's `_id`**: an id is a handle on the deleted row and a ledger full of them is a catalogue of what she erased. **Delete precedes ledger**, unlike the §22.4 age gate which audits first: a ledger row written first with a failed delete would tell a user her memory was gone while Tara still knew it. A failed ledger write logs loudly and does NOT fail the call — the memory is already gone.
- **The scoped verbs stay separate.** A conversation delete must NOT delete memories (`source_state: removed`, the memory survives); an unticked journal checkbox is INERT and does not even mark the source removed. `tests/memory/test_deletion_paths.py` asserts what survives as hard as what dies, and the negatives are the point.
- **§30.5's search is keyword+recency, deliberately.** That contract is one an exact scan satisfies EXACTLY, which is what makes the Community-mongo path honest rather than a toy — a BM25 score is not something it could reproduce, and §30.5 puts natural-language search in P1. **There is exactly ONE backend and `tests/journal/test_search_provenance.py` asserts it.** Atlas is deferred under release gate `journal.atlas_search`, which blocks **`scale`, not `closed_beta`** — filing a scale ceiling under a launch stage is how a real blocker gets tuned out. **Never add a capability probe here.** The memory module's probe is correct there; here it would select an unexercised `$search` path in production on the first real query, against an index nothing creates.
- **`SearchMode` is a parameter, not a setting.** §30.5 gives two answers over the same row — an explicit query returns her own L4 content because it is hers, a suggestion never resurfaces it. The search ROUTE passes `EXPLICIT` and there is no parameter that can change it; a mode a caller could pass is a mode an attacker could pass.
- **§32.15's deletion ORDER is chosen.** Ownership → birth details and charts (before the member row, so a mid-way failure leaves a member pointing at nothing rather than orphaned crown jewels pointing at nobody) → the ticked memories → the member row (which IS the removal from §28.2's `family_reminder`, since that reads this collection) → the attestation, **REVOKED and never deleted**. The last is §32.15's DPDP clause and the half a well-meaning "delete everything" gets wrong: the consent is a fact about the account-holder, the birth details were a fact about someone else.
- **"Memories about them" is a NAME MATCH, and that is why they are LISTED.** `memories` has no family-member field in §6.4, so the judgement is shown to the person whose memories they are. A silent name-matched delete would take "Sudha's birthday is 11 March" along with a stranger's remark containing the word.
- **§45's memorial conversion writes ONE field and touches nothing else.** `test_the_conversion_touches_exactly_one_field` compares the document before and after, so a future helpful addition fails there rather than in someone's family list. It writes no withdrawal (nothing was withdrawn) and is reversible — a wrong tap in the week after a death must not be another loss. The reminder exclusion is a QUERY (`living_members`), never a deletion: she stays in the list, the charts and every past artefact.
- **`astrology/kundli.py` selects by GRAHA IDENTITY, never by position** — the M6 lesson as a module. `tests/astrology/test_kundli.py`'s fixture is built to FAIL a positional read: facts emitted out of `Graha` order, every graha in a different house. No lagna means **no diamond** (§5.4); `build_moon_chart` is a separate function with a separate name because chandra lagna is a different chart, not a degraded one, and a `moon=True` flag would let a caller draw one without labelling it.
- **`AstrologyFacade.time_accuracy()` reads the STORED value.** `BirthInput` is narrowed to the five fields the engine needs and carries no accuracy, so a `getattr` against it returns a default for every user — and §30.2 stores a WINDOW for an approximate time, so the presence of a time proves nothing. Every approximate chart would have shipped labelled `verified`.
- **§10-17's "no streaks, no guilt" is enforced structurally.** `tests/reflection` asserts the dataclass fields, the service's public surface and the stored document carry no streak, completion or comparison. An earlier version grepped the source and tripped over its own prose explaining the absence — a test that cannot tell prose from code is one people learn to work around.
- **A reflection binds to the user's local date at CREATION** (§27). The route takes the date as a PATH parameter; a server that substituted its own would split a traveller's night across two rows.

## What the first live walkthrough found (M10) — invariants that must not regress
- **`AstrologyFacade`'s birth-row lookup must name the SUBJECT, not just the owner.** A family member's row carries `user_id` = the owner and `family_member_id` = the member, so `{"user_id": subject}` found nothing for a member (S28 declined with ASTRO_INSUFFICIENT_BIRTH_DATA while the screen said "Birth details on file") **and** could return a MEMBER's row for the owner's own chart — natural order, every confidence chip reading `verified`, your mother's chart shown as yours. `_subject_query` is the one place; the own-branch pins `family_member_id: None`, which the WRITE path always did.
- **`place_label` is resolved SERVER-SIDE** (`chat_orchestration/birth.place_label_for`). It arrived only in the request body and no client sends one, so every live turn ran with `has_current_location: False` and S18's first suggestion chip was answered "Which city should I use?" against an account whose city was stored. Exactly `birth_profile_for`'s own lesson one field over, and invisible for the same reason: every test passes one explicitly. A caller-supplied place still wins (§30.2 lets a question name its own city); a TIMEZONE is never used as one.
- **A brief read back from the store must be HYDRATED with its snapshots.** §6.4 puts ids on `daily_briefings` and snapshots in `guidance_logs` (§34.2). The panchang row, S16's timings and Tara's cited line are all built from the SNAPSHOTS, so a freshly generated morning looked perfect and the same morning reloaded lost its panchang strip. `BriefStore._hydrate` reads them back — never RECOMPUTES them, which is the whole reason the two collections are separate — and attaches all-or-nothing per module, because `fact_ids` prefers snapshots and a partial attach would SHRINK the citation list.
- **The brief's fact stage must ask for day timings SEPARATELY.** `PanchangService.panchang` passes `include_day_timings=False`; the timings come from `day_timings()`. Nothing called it, so no brief ever carried a timing fact, `TodayPayload.timings` was empty for every user every morning, and `/today/timings` served §24.6's "the panchang cell was cold" state permanently. Fixing it also made `favourable_window`, `caution_window` and `hold_off` reachable in a real brief for the first time.

## payments module (M11, §30.3/§22.13/§22.1) — invariants that must not regress
- **The rails are DECLARED and the simulator is the only IMPLEMENTED arm.** `payments/providers/routing.py` is a `(provider, region) → Support` matrix whose `resolve()` may return NO provider and takes no fallback parameter — the same shape, and the same rule, as `voice/providers/routing.py`. A payment rail's silent fallback is worse than a recogniser's: §22.1 makes India INR-with-GST through Razorpay and the diaspora USD-zero-rated-under-LUT through Stripe India, which are different legal postures, so a fallback between them is a compliance event rather than a degraded experience. **There is no `or SIMULATOR` anywhere**, and a test parses the module's AST to keep it that way. Landing a real rail is ONE cell plus an adapter; `test_landing_razorpay_is_ONE_cell` asserts it literally and restores the matrix in a `finally`.
- **`payments/service.py` never names a rail.** No `if provider is RAZORPAY`, no `if simulated`. That is what makes the one-cell promise true rather than aspirational.
- **`razorpay.py` and `stripe.py` raise on every method.** Two guards, deliberately, because they fail differently: the matrix keeps them out of the product, and the raise keeps a future caller that constructs one directly — which is how "a quick test against the real thing" gets written — from silently doing nothing and reporting success. Their headers list what closing the gap actually needs, most of which is not code.
- **The simulator verifies a REAL HMAC.** §13 requires webhook signature verification on both rails, and an unverified webhook is an unauthenticated instruction to grant paid access. A simulator that accepted anything would leave that path unexercised until the day a real rail arrived. The dev control surface signs and POSTs rather than calling `handle_event` directly, for exactly that reason.
- **The simulator has NO randomness.** Every behaviour is a fault someone armed. A demo must be able to show a specific state on demand, and a state machine that sometimes does something else is one whose failures cannot be reproduced by the person who just saw one.
- **The interface has nowhere to put an instrument** (§13, PCI SAQ-A). No card, PAN, CVV or VPA field exists in `PurchaseRequest`, `PurchaseIntent`, `ProviderEvent` or `RefundRequest`; collection happens on the rail's hosted surface and `checkout_url` is the whole mechanism. A test asserts the field sets. `instrument_ref` is a rail-side TOKEN, CSFLE-encrypted under the `payment` key class.
- **The two duplicate questions are different, and their ORDER is load-bearing.** `provider_event_id` (uniq, §6.4) catches a REDELIVERY; our `idempotency_key` catches two genuinely distinct events that both charged for one purchase, which §30.3 refunds rather than ignores. Asking the second first makes every ordinary rail retry look like a second charge and hands money back to someone who paid once — it did, until `test_a_duplicate_CHARGE_is_refunded` caught it. Redelivery first, then record, then `has_other_charge(excluding_event_id=…)`, which needs the exclusion because the row it asks about is already written.
- **The duplicate guard is the INDEX, not the read.** `record_event` inserts and catches `DuplicateKeyError`; between a check and an insert is where two webhook deliveries in two workers collide. `_skip_precheck` exists so one test can force that race.
- **`lifecycle.py` is pure and clock-injected, and `access_at` COMPUTES rather than reading a stored status.** A stale `grace` the sweep has not advanced is a real state a real process reads; answering from it grants full access weeks after a downgrade. The mirror also binds: nothing may revoke early. §22.13's grace is FULL access for seven days — not "most", not "new guidance only" — and the tests check every day boundary rather than the two ends, because the failure worth catching is an off-by-one that revokes on day 6.
- **`grace` and `read_only` are separate states because §22.13 gives them different promises.** A single "past due" flag with a day counter beside it is a shape in which any comparison that reads the flag and forgets the counter conflates them. `read_only` maps to §28.2's `free` variant, never to `grace` — mapping it to `grace` would show an amber banner about features she no longer has.
- **`fail_renewal` touches nothing but the status and the clock.** Not `period_end`: a failed renewal is a fact about the NEXT transaction and the period she paid for is a fact about a completed one. A second failure does NOT restart the clock, or a rail retrying daily would hold someone in grace forever — the generous-looking version of never downgrading anyone, and equally a bug.
- **`renew` anchors the new period on the OLD `period_end`, never on `now`.** Anchoring on the collection instant walks every subscriber's renewal date forward by however long their bank took, permanently and by more every cycle. It is also what makes a recovery inside the grace whole.
- **`subscriptions.live` is derived from the status in exactly ONE place** (`lifecycle.is_live`, applied by `store._state_fields`) and carries a second partial unique index. §6.4's index is `user_id+status where status=active`, written when a subscription had two states; §22.13 grants access under `trialing`, `grace`, `read_only` and `cancelled` too, and every one is a row a second purchase could be made alongside — two rows granting access and a renewal job billing both. A test asserts every access-granting status is live.
- **Money is integer minor units and two currencies never meet.** `Money` raises on any cross-currency operation and **there is no exchange rate anywhere in the package** — a test greps for one. §30.3 forbids conversion in four separate sentences, and the one place it contemplates a cross-currency event (a gift) is handled by not converting: `lifecycle.extend` takes DAYS, because time has no currency. That is the only way §10-20's NRI case (buy USD, redeem India) and "retains its original currency" are both true.
- **An undeclared price DECLINES** (`NoSuchPrice`). No default, no nearest region, no monthly × 12. §22.1 settles tax internationally (zero-rated export under LUT); the India GST RATE is not in the spec and is `payments.gst_invoice_rate`, not a plausible 18%.
- **A gift claim is a compare-and-swap** (`redeemed_by_user_id: None` in the filter), and it happens BEFORE the extension. Read-then-write would let two simultaneous redemptions of one code produce two extensions from one purchase. Expired, used and unknown all answer with ONE `message_key` — a response that distinguished them is an oracle for enumerating bearer instruments.
- **`migrate_region` REFUSES mid-cycle rather than deferring.** §30.3's rule is about the instant, not the intention, and a function that accepted at any time and quietly scheduled is one whose callers stop knowing when it takes effect. It drops `founding` always (§30.3: promotional pricing does not transfer across regions).
- **`dev_router` is dev-only and moves the ROW's clock, never the process clock.** Monkeypatching `datetime.now` would move it for §7.1's brief scheduler and §32.13's date binding too, and a demo whose morning brief silently regenerated for a different day would be demonstrating a bug that is not there.
- **Release gates:** `payments.live_rails` reads the capability matrix, so it closes itself; `payments.gst_invoice_rate` waits on finance. Both block closed beta. `release_gates.py` imports neither the dev router nor `prototype`, and a test asserts it.

## notifications module (M12, §23/§32.6) — invariants that must not regress
- **§23.1's four classes are a TABLE (`classes.py`), and §23.5's five categories are a different set.** A class is behaviour the code hard-codes ("not configurable per template"); a category is a choice the user makes. §23.5 offers no toggle for Class T at all, and splits Class C into `contextual` and `festival`. Three import-time asserts hold the table: exactly ONE class bypasses quiet hours + the 3/day cap + suppression, Class T may never carry marketing (it is the class a win-back would be routed through, and §22.13's dunning being legitimately Class T makes that live), and the T>D>C>M priorities have no ties.
- **§23.2's trigger 1 is Class T, and `consumes_slot` is DERIVED from that, never listed.** §23.2 gives ONE reason for the exemption — "it is Class T, user-initiated" — so quiet-hours exemption, cap exemption and slot exemption are one cell with three consequences. A hand-written `consumes_slot=False` beside it is a place for the two to disagree, and the disagreement looks like a cap breach. The consequence to keep in mind: **three reminders plus a festival greeting is four messages and is not a breach.**
- **§32.6's exemption belongs to the APPOINTMENT, not to the class and not to the category.** A Class-D flag would exempt the NIGHT NUDGE, which §23.4 expires at 23:30 — one hour inside the default 22:30 window. `may_send` grants it only when the send's local time equals the resolved appointment, and there is no argument that widens it.
- **The appointment is RESOLVED per date (`appointment_local_time`), never the raw `brief_time` string.** §7.1's `local_instant` advances a DST-gap brief: on 2026-03-08 in New York an 02:30 brief is scheduled for 03:00, because 02:30 does not happen. Comparing against the string held the brief in quiet hours and it expired at noon — once a year, silently, only for users whose brief time sits inside their quiet hours. **The §23.9 timezone matrix found it; no unit test could have, because every one of them passes a brief time that exists.**
- **`ladder.build` takes the message class as a PARAMETER.** Deriving it from the category gave §23.2(1)'s reminder Class C's first-success mode instead of §23.3's transactional fan-out — the reminder still arrived, on one channel, indistinguishable from a daily-loop message. `SendRequest.message_class` is the one place the class is decided.
- **§23.3 has THREE ladder shapes and they are not interchangeable.** FIRST_SUCCESS for D/C ("same message, NOT both"), FANOUT for T ("deliberate redundancy"), CONSENTED_ONLY for M ("no fallback"). One "try each in turn" list breaks each in its own direction: a brief goes out twice, a payment failure goes out once, a marketing message falls onto a channel nobody consented to.
- **The §23.1 gates run in ONE order and quiet hours come BEFORE the caps.** Reversed, three held messages exhaust a cap nothing ever used and the user receives nothing all day while the ledger says she hit her limit. §23.7's halt is first because it is an operator saying "stop" during an incident.
- **The ledger row is written BEFORE delivery.** A row written after a successful send does not exist if the process dies in between, and the retry then has no idempotency collision and nothing stopping a second delivery. The accepted trade: a worker that dies between a push and `mark_sent` leaves ONE delivery and a row still reading `queued`. §23.8 is slightly pessimistic; nobody is messaged twice. §23.9 makes the reverse release-blocking.
- **§23.3's dedupe key carries NO channel** (`user+message_id`, Redis, 24h). A per-channel key is satisfied separately by every rung — the exact double-send it exists to prevent. A message that reached nobody RELEASES the claim: the key stops a second delivery, not a first.
- **§23.6 has two deaths and they are not one.** 404/410 retires a subscription on the FIRST occurrence; three CONSECUTIVE transient failures retire it, and any success resets the counter. **A REJECTION (400/401/403) counts toward neither** — a mis-rotated VAPID key makes every push 403, and counting those would retire every subscription in the database in three mornings over a five-minute configuration error.
- **The caps are `count_documents` against the ledger, never a counter beside it**, and every window is the USER's local day. A UTC day gives a Mumbai user two different caps depending on the hour. The count includes `sent`+`delivered` and excludes `queued` — a queued row that will be superseded reaches nobody and must not spend a slot.
- **`webpush.py` is the real protocol, not a simulator, because web push needs no vendor account.** The push service is the browser's own and VAPID is a self-generated keypair. `tests/notifications/test_channels.py` decrypts **RFC 8291's own published test vector** with our key derivation — the one test that catches a wrong KDF, which otherwise has no symptom at all: the service returns 201, the browser silently drops the payload, the phone stays quiet.
- **The VAPID keypair is persisted, never generated at boot**, and `--generate` refuses to overwrite. A subscription is bound to the `applicationServerKey` it was created with, so a key that changed on restart invalidates every subscription in the database.
- **`SmtpChannel._build` sets the BODY first.** `set_content()` calls `clear_content()`, which strips every `Content-*` header including `Content-Language`. Headers-then-body silently drops the locale and nothing about the message looks wrong afterwards.
- **WhatsApp is DECLARED and gets §30.3's exact treatment.** `providers/routing.py` is a `(provider, channel) → Support` matrix with no fallback parameter and no `or SMTP`; `whatsapp.py`'s constructor raises. Landing it is ONE cell plus an adapter, and `notifications/service.py` does not change — it has never known which channel answered. The gate READS the matrix, so it closes itself. **A DECLARED channel is filtered out of the ladder rather than failing it**, so a user with "morning × whatsapp" switched on still gets her brief and keeps the preference.
- **§23.7's emergency stop fails OPEN.** Failing closed would let a Redis blip silence every OTP, payment failure and L4 safety resource in the product with nobody having decided that. It has no TTL — a halt that lapsed on its own would return at the worst moment with the operator believing it was still in force.
- **Notification copy is SERVER-rendered and sits in `SERVER_RENDERED_KEYS`.** A service worker has no catalog and §2.4 has no English fallback, so a missing Hindi string is an English notification on a Hindi lock screen, outside the app, at 07:00. A missing key is a BOOT failure.
- **No notification interpolates an astrological claim.** §5.3's cite-or-die does not run on a push payload, so a claim on a lock screen would be the one uncited sentence in the product. A push says the brief is ready; the claim lives behind the deep link where the validator runs.
- **Deep links are ROUTES, never origins**, in the payload and in `sw.js`. A push that could carry an absolute URL could navigate a browser off our domain.
- **Release gates:** `notifications.whatsapp_channel` (reads the matrix, self-closing), `notifications.copy_review` (§14 native reviewer), `notifications.trigger_sample_floor` (§23.2 states no minimum sample, so a trigger that sent once and was not opened pauses for a fortnight — worst at beta volumes, which is why it blocks closed beta). All three block closed beta.

## daily_guidance module (M6, §7.1) — invariants that must not regress
- **`windows.py` is pure and clock-driven.** No database, no Celery, no network — a DST boundary at the date line is a hard case to reason about and a trivial one to reproduce. `tests/daily_guidance/test_windows.py` IS §23.9's timezone matrix for the selection half.
- **The lead window is a SCHEDULE, not a filter** (CL-008 §1). A 60-minute window sampled every 15 minutes contains each user for FOUR ticks; the `lead_minutes` hash picks the ONE tick they fire on. `blake2b`, never `hash()` — the built-in is salted per process, so every worker would draw a different slot and the smoothing would become noise.
- **`local_instant` returns UTC, always.** PEP 495 makes an aware datetime that is AMBIGUOUS in its zone compare unequal to its own instant elsewhere while comparing neither less nor greater — trichotomy fails and every `==`, `in`, dict key and sort over it is quietly wrong twice a year. The test demonstrates the hazard before asserting the guard.
- **The ranking engine emits ONLY `MorningModule`** (§34.3) and only where the evidence is in hand (§5.3). `MODULE_FACT_KINDS` declares what each of the seventeen may stand on; two import-time asserts keep every module reachable from exactly one density bucket and gated by a declared requirement. **Density caps the COUNT, never the facts** (§28.2).
- **Composition happens before the model, from facts alone.** That is what makes §7.1's degrade cheap: falling back to composed text can never ship an uncited claim, because composed text is where the citations come from. `tests/…/test_templates_and_polish.py` runs the engine's own sentences through the chat pipeline's grounding validator, in all three locales.
- **The citation goes INSIDE the sentence**, before the full stop. The validator splits on punctuation, so a trailing marker is a second "sentence" and the claim reads as uncited — perfectly cited text failing its own gate.
- **A module composed from snapshots must come back citing one** (CL-008 §4). Structural, checked before the vocabulary test: `GroundingValidator` decides claim-hood from words, so a times-only sentence passes uncited — an edge case in chat, every morning in a template.
- **Four outcomes, and they are not interchangeable.** POLISHED · RANKING_ONLY (§7.1's COST LEVER, and the §8 provider-outage path) · VERIFIED_CORE_CARDS (§7.1's DEGRADE — diagram 5's `fail` edge, or facts too thin) · FAILED. **An outage is not a grounding failure** — `PolishReport.all_rejected` excludes it deliberately.
- **The DEGRADE has two entrances and the second one was missing.** The grounding `fail` edge worked; "facts too thin" could not fire, because `rank`'s base modules are a superset of what `core_cards` wants under the same `emittable` gate — so a fact set that leaves `rank` empty leaves `core_cards` empty too and lands on FAILED. The one way through was an accident of density (LOW skips the panchang row), which meant two users with identical evidence got different honesty. `_is_core_cards_only` is the real trigger and it needs BOTH halves: the fact stage named something missing, AND nothing beyond `ranking.CORE_CARD_MODULES` survived. A core-cards-only morning with every fact in hand is a quiet LOW-density day, not a failure.
- **The three fact-free modules need `available_inputs`, and nothing built it.** `priorities`, `goal_check` and `family_reminder` were structurally unreachable in a real brief for three milestones. `personal_inputs.load_inputs` is the loader, called by BOTH generation paths (the scheduled task and `/v1/today`'s on-open). A slug is not a sentence (localise `profiles.priorities` through `start.priorities.option.*`), a goal is already in the user's words (verbatim, never translated), and a CSFLE name that reads back as ciphertext declines rather than composing a card around a blob.
- **§32.13's key has three components; the unique index has two** (CL-008 §3). Locale rides inside the stored key so §32.7 can tell a stale-language row from a current one; `(user_id, date)` stays unique so a locale change REPLACES rather than duplicates. The §23.4 collapse key omits locale for the mirror-image reason.
- **`brief_time` is zero-padded local "HH:MM"** and the padding is load-bearing: the §7.1 index does a STRING range scan, and unpadded "7:00" sorts after "10:00".
- **Dormancy is the residual tier** (CL-008 §2), never orthogonal to payment — a paying subscriber on holiday must not lose the mornings they paid for.
- **The pre-job works over CELLS, not users.** §7.2's key carries no user by construction, so a city of ten thousand costs what a city of one costs. A pre-job iterating users would produce identical output at ten thousand times the price and nothing downstream would notice.
- **Chart facts ARE wired** — `astrology/chart_adapter.py` calls sitara-astro for natal, dasha and transits, and `CompositeBriefFacts` fetches both halves independently so neither takes the other down. `BriefFacts.missing` names whichever failed, which is what `_missing_reason` reads. (This line said the opposite through M6–M8; it was stale, not a decision.)

## today module (M8-P9b, §28.2/§29.1) — invariants that must not regress
- **`GET /v1/today` is the door M6 never had.** M6 stored `daily_briefings` rows nothing could read. The router is deliberately thin: `BriefStore.get` on the user's LOCAL date (§32.13, never UTC), `generate_on_open` on a miss (§7.1's dormant path and §32.13's missed-date path are one code path), `mark_opened`, serialise. Every other decision is made somewhere better.
- **A failed brief is a SCREEN, not a 5xx.** §28.2 has a designed variant for every way this goes wrong. Returning an error envelope from `/v1/today` would replace a designed state with an error page on the app's home surface.
- **The brief enums live in `sitara_schemas.today`, not here.** `Density`, `Tier`, `BriefStatus` and `BriefDegradeReason` cross the wire, so both sides need one declaration — the same discipline §34.3's `MorningModule` already follows. `types.py` imports and re-exports them; it declares none.
- **`variant` is NOT a payload field.** §32.1's precedence is a rule over `TodayState`, evaluated once in `apps/web/src/lib/today-variant.ts` where the stack is rendered. A server that also picked the variant would be a second implementation, and the two would disagree on exactly the crowded morning the rule exists for.
- **`compose_brief` is the ladder without the store.** Split out of `generate_for` so the four outcomes are reachable with no database, no queue and no clock — which is what let the dev router run the REAL ladder instead of needing a fake `BriefStore`.
- **A festival is nudged, not bypassed.** `_relevance_for` raises `festival_observance`'s relevance when the fact is present, because §28.2 puts a festival on two surfaces and at MED density the card otherwise loses the cut to `family_reminder` — a festival morning rendering no festival anywhere. It is still gated on having the fact (§5.3).
- **Tara's line is NOT an eighteenth module.** §28.2 item (2) is composed by `templates.compose_taras_line` in two registers: cited when it leans on the day, claimless when there are no facts. The claimless register is what makes "always present" compatible with cite-or-die. **A cited line must be ONE sentence** — `_cite` puts the marker before the final stop, so a two-sentence line leaves the claim in sentence one uncited. A parametrised test over every band × locale caught exactly that.
- **`sources_line` is derived from the CONFIDENCE STATE, not the snapshot count.** A module's snapshot count is how many different facts it stands on, not how many sources agreed on one — reading it produced a Trust Sheet saying "checked against two sources" directly above "one source available today". §32.2 already encodes corroboration in the state.
- **`dev_router` is dev-only and mounted by `app.py` only when `environment == "dev"`** — `db.seed`'s rule. It fixes only the FACTS and the account state (`dev_fixtures.py`) and runs the real ranking engine, composer and ladder over them. It carries **no stub model at all**: once the partial degrade path existed, `provider_degraded` reached VERIFIED_CORE_CARDS through the real ladder, and the ungrounded-LLM stub it used to need was deleted.
- **The web's fixtures are RECORDED, never authored.** `scripts/record_today_fixtures.py` writes `apps/web/tests/__fixtures__/today/` from the real pipeline; `stub-api.mjs` replays them. Re-record after any template, ranking or ladder change — the diff is the review artefact.

## memory consolidation (M6, diagram 8) — invariants that must not regress
- **Consolidation never deletes.** Same rule `decay.py` established: §32.4 retains "until user deletes". A duplicate is FOLDED — muted, kept in the vault, pointing at its canonical — because the user consented to each copy separately.
- **The canonical is elected per CLUSTER, not per pair.** Pairwise folding builds chains (A→B, then B→C) that leave a duplicate pointing at a duplicate. Single-link clustering then one election makes that unrepresentable.
- **A muted memory is never folded into** — unmuting must not restore a pointer.
- **`theme_label` is TOP-LEVEL and encrypted**; everything else consolidation writes lives in `consolidation` and is metadata only. The explicit codec reaches top-level paths and not nested ones (§36.3), so a nested label would silently never be encrypted — and a theme name is memory content in summary form.
- **No model, no label.** An unlabelled theme is a real theme; an invented one would be a summary of the user's life that nobody wrote.
- **Nothing crosses an embedding space or a §32.4 type** — cosine across spaces is noise, and noise that clusters looks exactly like insight.

## scheduling module (M6, §6.1/§23.7)
- **Exactly one Beat may run.** Two would double-fire every §7.1 wave. The compose stack runs `beat` as its own single container.
- **Every task must be safe to run twice.** §6.1 rejected a workflow engine on the strength of "Celery Beat + idempotent tasks", and `task_acks_late` means a dead worker hands the message back.
- **The tick fans out by `send_task` name**, so the producer needs none of the consumer's imports and can run on a worker carrying no model client.
